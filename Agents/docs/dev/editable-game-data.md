# Editable game data

**Status: in progress (mod roll ranges, item limits, and the unique/jewel/tattoo catalogue rows are editable; item
templates and the admin UI are next).** This page analyses what can safely become editable from the database, what
cannot, and the cache/reload shape the server uses so an edit takes effect without a restart. The schema and the
`/game_data` commands below are implemented; item templates are only the planned shape.

## Goal

Make a useful part of the server's reference data editable at runtime:

- mod roll ranges (the `Stat1Min`/`Stat1Max` pairs), so a server owner can widen or narrow a roll without regenerating
  the extracted tables;
- item limits (radius jewels, timeless jewels, Impossible Escape, tattoos), so the server can allow or forbid more than
  one copy;
- custom item templates built from existing client-known bases, mods, art and words;
- later, other server-side settings: drop chances, vendor prices, crafting costs and similar.

The reference data (the mod list, base types, tag lists and generated tables) must stay in memory. Hot paths must not
query SQLite per roll, per item or per socket check. An edit through a command or a future admin panel must publish a new
in-memory snapshot atomically; a reader either sees the old snapshot or the new one, never a half-applied change.

## What exists today

- Game data is **JSON under `data/tables/`**, generated by `scripts/dev/extract-data.ps1`. It is not in SQLite.
- `data/saves.db` is SQLite (`SaveDatabase`): characters, account characters, accounts, stashes, stash tabs, deleted
  characters and `meta`. The overlay adds `game_data_meta`, `mod_stat_overrides`, `limit_overrides`, `catalog_entries`
  and (schema only, pending item templates) `item_templates` to the same file.
- `ModCatalog` loads `Mods.json`, `Stats.json`, `Tags.json` and `ModType.json` into immutable `Mod` records. A
  `ModStat` carries `Id`, `Min`, `Max` and `Local`.
- `ItemCatalog` loads `BaseItemTypes.json`, `item-types.json`, `ItemVisualIdentity.json`, `CurrencyItems.json`,
  `ComponentCharges.json` and item component data into immutable `BaseType` records. `BaseType.Implicits` holds
  `ModCatalog.Mod` references, and `ItemCatalog.Create` rolls those implicits.
- `ItemRolls` builds a weighted prefix/suffix pool per `(base row, item level)` and caches it in a
  `ConcurrentDictionary`. The cache stores mod references and weights, not rolled values.
- Unique and jewel catalogues are mostly **static arrays in code**: `UniqueCatalog` (two definitions),
  `RadiusJewelCatalogue` (radius jewels and their `Limit`), `UniqueJewelCatalogue`, `ImpossibleEscapeCatalogue`,
  `TimelessJewelCatalog`, `ThresholdJewelCatalogue` and `UniqueJewelVisuals`.
- Limits are enforced in code: `Program.Items.PassiveJewelRefusal` has a hard-coded one-Historic-timeless-jewel rule and
  one Impossible Escape rule; `RadiusJewelCatalogue.Entry.Limit` is checked there; `Program.Tattoos` checks the 50 cap
  and the five `PassiveSkillOverrides.Limit` groups.
- The Gateway opens `data/saves.db` once (`Saves.Open`) and shares one `SaveDatabase` connection. Auth opens the same
  database for account/character rows. SQLite is in WAL mode with `synchronous=FULL` and a 10 s busy timeout.
- Catalogues are **lazy**: `Lazy<T>`/`ConcurrentDictionary` load on first use and never invalidate. `Program.Items`,
  `Program.Rolls`, `Program.Uniques`, `Program.Passives`, `Program.TimelessJewels` and the other `Program` statics are
  process-wide.

The client has its own copies of `BaseItemTypes`, `Mods`, `Stats`, `Words`, `ItemVisualIdentity` and the other data
tables. The server can only create items the client can resolve by an existing hash. That is the main boundary below.

## What can be edited safely

| Area | Editable at runtime | Why |
|---|---|---|
| Mod stat roll ranges (`Stat{n}Min`/`Max`) | **Yes** | The client receives the rolled values with the item; it does not need the server's range. New rolls and max-roll dev commands can use the override. |
| Mod level, spawn weights, generation weights, tags, families, essence-only, generation type/domain | **Yes, server-side** | These decide what the server may generate. The client identifies a mod by its hash and reads its stat keys, not its spawn metadata. Changing them can make a mod appear that the client did not expect but can still display. |
| Mod stat keys and mod hash/Id | **No** | The client looks the mod up by `HASH16` and reads the stat keys in its own order. Rewriting either desynchronises the item. |
| Unique/radius/timeless definitions that reuse existing base types, mod hashes, art and word hashes | **Yes** | The item wire data is made of existing client records. The server decides the values and the limit. |
| Item limits (radius jewels, timeless, Impossible Escape, tattoos) | **Yes** | The limit is enforced by the server. The client tooltip may still print its own limit text; that is display data, not enforcement. |
| Custom item name | **Yes** | `MagicProperties.Write` already has the client's custom-name bit (`0x80`, a length-prefixed string). `Item` does not expose it yet; adding a `CustomName` field and saving it is enough. |
| Custom item from an existing base + existing mods + explicit values | **Yes** | This is what `/mod` does manually today. A template table makes it repeatable. |
| Drop chances, vendor prices, crafting costs | **Yes, later** | Server-only decisions. They need their own typed settings and tests. |
| Base item name, hash, class, width/height, components, tags, visual identity | **No** | The client owns these and renders the item from them. A server-only change desynchronises the inventory, tooltip or model. |
| New base item types, new mod rows, new word hashes, new art | **No** | The client has no row for them. A new HASH32/HASH16 is an unknown object to the client. Use an existing base/mod/word/visual instead. |
| New stat keys or changed stat semantics | **No** | The client and the server's consumers both key behaviour by `Stats.dat` Id/row. This is code, not a data edit. |
| Stack size, max stack, inventory shape, item class | **No / restricted** | The client's inventory UI and item component reader use their own values. Only change these if the client table is changed too. |

Do not change client-owned models/art. |
| Drop tables and rates | `ItemDrops.Currency`, `EquipmentClasses`, `NotDropped`, `EquipmentRarity` | **Yes** | Server-only loot policy; high value for balance. The drop table can be typed rows with weights, level caps and enabled flags. |

| Gem/utility/monster mapping lists | `GemSources.DropOnlySupports`, `GemSupportDamage.Unconditional`, `UtilityFlasks.Modelled`/`PanelOnly`/`DuringEffect`, `MonsterMods.Modelled`/`Vacuous`/`SelfAuraMods`, `HarvestCrafting.Metamods`, `EssenceCrafting.Columns`, `SkillCatalog.ProjectileFallbacks` | **Yes, later** | These are server mapping tables. Move one typed family at a time with tests; the consumers are code. |
| Ruthless/league policy lists | `RuthlessGemRules.UnavailableBases`, `UnavailableEffects`; `SingleUseCooldown.Unsupported`; `GemVendorStock` | **Yes, later** | Policy/config, not client data. |
| Charge/damage/panel rule lists | `ChargeEffects`, `ChargeGains`, `DamageImmunities`, `PanelStats.Sums`, `StatKeys` | **No as raw tables, low priority** | They encode calculation order and stat semantics. A data-driven rule engine would be a separate, tested project. |
| Protocol and component lists | message ids, `InstanceItems.ComponentOrder`, `BaseComponents`, `PlayerDefaults`, packet layouts | **No** | The client and the server must agree exactly; these are code/protocol, not user settings. |
| Terrain/RNG tables | `EdgeShaping`, `TileKey`, pathfinder tables, level-generator constants | **No** | Reverse-engineered algorithms; changing them needs a generator gate and baseline, not a settings table. |
| Client-owned hashes, names, geometry, art, stat keys | `BaseItemTypes`, `Mods`, `Stats`, `Words`, `ItemVisualIdentity`, item components | **No** | A server-only edit desynchronises the client. Keep the extracted JSON as the reference. |

The practical split is:

- **Content catalogues** (uniques, jewels, tattoo effects, shops, drops): move to typed tables, seeded from the current
  code/JSON, loaded into immutable snapshots.
- **Server policy** (rates, limits, counts, costs): typed settings with defaults in code and database overrides.
- **Client protocol** (hash ids, component order, stat keys, packet layouts): never in the settings database.
- **Algorithms** (damage, charges, level generation): only through a tested data-driven rewrite, not as a list edit.

### What "custom item" can mean

A custom item can be:

- an existing base type (`Metadata/Items/...`), with any mix of existing mod HASH16s, explicit values, rarity, item
  level, quality, sockets and links;
- a custom display name, sent through the item's custom-name bit (the server needs a `CustomName` field);
- existing art and existing word hashes (or none, when a custom name is used);
- a template in SQLite so it can be recreated or handed out by a command, drop rule or admin panel.

It cannot be a new base type with a new HASH32, a new mod with a new HASH16, or a new stat key. Those need a client data
patch, not a runtime server setting.

## Database shape

Keep the extracted JSON as the immutable reference. The SQLite tables are an **overlay** loaded at startup. The
`data/tables/` files are not rewritten by the server.

Suggested tables (names can change during review):

```sql
CREATE TABLE IF NOT EXISTS game_data_meta (
    key TEXT PRIMARY KEY,                 -- schema_version, revision
    value TEXT NOT NULL
) STRICT;

CREATE TABLE IF NOT EXISTS mod_stat_overrides (
    mod_id TEXT NOT NULL,                 -- Mods.dat Id, e.g. LocalAddedPhysicalDamage9
    stat_index INTEGER NOT NULL,          -- 0-based position in the mod's stat list
    minimum INTEGER NOT NULL,
    maximum INTEGER NOT NULL,
    updated_utc TEXT NOT NULL,
    PRIMARY KEY (mod_id, stat_index)
) STRICT;

CREATE TABLE IF NOT EXISTS limit_overrides (
    key TEXT PRIMARY KEY,                 -- timeless_jewel, impossible_escape, radius:Impossible Escape, tattoo:...
    value INTEGER NOT NULL,               -- 0 = unlimited, positive = maximum
    updated_utc TEXT NOT NULL
) STRICT;

CREATE TABLE IF NOT EXISTS catalog_entries (
    kind TEXT NOT NULL,                   -- unique_item, radius_jewel, threshold_jewel, unique_jewel_global, ...
    key TEXT NOT NULL,                    -- name, or name|base where a name repeats (Combat Focus)
    payload TEXT NOT NULL,                -- the typed row as JSON
    enabled INTEGER NOT NULL,
    updated_utc TEXT NOT NULL,
    PRIMARY KEY (kind, key)
) STRICT;

CREATE TABLE IF NOT EXISTS item_templates (
    id TEXT PRIMARY KEY,                  -- admin id, e.g. fire_wand
    label TEXT NOT NULL,                  -- admin label, not sent to the client
    base_type TEXT NOT NULL,              -- existing BaseItemTypes Id
    rarity INTEGER NOT NULL,
    item_level INTEGER NOT NULL,
    quality INTEGER NOT NULL,
    custom_name TEXT,                     -- null = use words/base name
    name_words TEXT,                      -- JSON array of existing Words HASH32 values
    visual INTEGER,                       -- existing ItemVisualIdentity HASH16, null = base art
    corrupted INTEGER NOT NULL,
    mirrored INTEGER NOT NULL,
    mods TEXT NOT NULL,                   -- JSON [{id, section, values:[...]}]
    updated_utc TEXT NOT NULL
) STRICT;
```

A generic `settings(key, value)` table can come later. Typed tables are preferred for validation and for an admin panel
that lists fields instead of raw JSON.

The existing `data/saves.db` is a reasonable home: it is already the shared local SQLite file, already in WAL mode and
already ignored by git. A separate `data/game-data.db` is an alternative if mixing save and configuration schemas is
unwanted; the code should not depend on which file is chosen, only on a `GameDataStore` path.

## Runtime model

### Reference snapshot

At Gateway startup, before the first item is created:

1. load the reference JSON into memory (the existing `ModCatalog`/`ItemCatalog`/catalogues);
2. load every override row from SQLite once;
3. apply the overrides to the in-memory model;
4. publish an immutable `GameDataSnapshot` containing the effective mod ranges, limits, item templates and the schema
   revision.

The item/jewel catalogues are one more snapshot: `catalog_entries` rows are seeded from the current code arrays on the
first run of each kind (`catalog_seeded:<kind>` in `game_data_meta`), then loaded as typed rows. The code arrays remain
the fresh-database seed; after that the database is the runtime source. A kind with all rows deleted stays empty instead
of being re-seeded silently.

`Mod` keeps its base `ModStat` values. The effective range is resolved through a `ModRangeProvider` held by the
`ModCatalog`:

```
base Min/Max (from Mods.json) -> provider.Range(modId, index) -> effective Min/Max
```

This means an override can change a roll immediately without rebuilding the `Mod` objects or `BaseType.Implicits`.
Every consumer that reads a range must go through the provider:

- `Mod.Roll` and `Mod.With` (the generation path);
- `UniqueCatalog` max rolls;
- `ImpossibleEscapeCatalogue` max values;
- `Program.Items` max-roll dev item creation;
- `RadiusJewelCatalogue` max rolls;
- `VendorRecipes` range checks;
- `BenchCrafting` range checks;
- tests that read a range.

A helper such as `Mod.EffectiveRange(index)`/`Mod.MaxValues()` keeps those call sites consistent.

### Cache invalidation

- **Mod ranges**: the provider holds an immutable dictionary. A change writes SQLite, rebuilds the dictionary and
  atomically swaps the reference. `ItemRolls` does not need clearing for ranges because its pool stores mod references,
  not rolled values. If an edit changes a mod's tags/weights, clear the pool cache (or key it by the snapshot revision).
- **Limits**: a `LimitSettings` snapshot with an atomic swap. The socket and tattoo checks read it per action, so no
  other cache is involved.
- **Item templates**: an immutable dictionary keyed by template id; a change swaps it. Item creation reads the current
  snapshot once and builds the item.
- **Reference catalogues**: `GameDataCatalog` loads the typed rows into arrays/dictionaries and swaps them together.
  `UniqueCatalog`, `RadiusJewelCatalogue`, `ThresholdJewelCatalogue`, `UniqueJewelCatalogue`, `TimelessJewelCatalog`,
  `TattooStats` and `UniqueJewelVisuals` read the current snapshot. Existing items keep their stored values; new items
  and new drops use the new definition. Do not mutate a `Lazy<T>` in place.
- **Threading**: readers take one snapshot reference (a `Volatile.Read`/`Interlocked` exchange). Writers serialize
  through the store; a failed validation or a failed SQLite commit leaves the old snapshot in place and reports the
  error. Never write a row first and then fail to rebuild the model silently.

The existing `Lazy<T>` fields are fine for the initial load, but they are not a reload mechanism. A reload should not
call `Lazy.Value` again; it should replace a snapshot field.

### Startup order

`Program` already opens the save database before serving. The game-data store opens after it, loads the overrides and
warms the reference data the admin panel needs (mod list, base list, tags, existing limits). That warm-up is one read per
catalogue, not a query per item. The first connection then sees the same snapshot.

### Interface

The first interface is the developer chat command (implemented):

- `/game_data list` — the current revision and the rows in the snapshot;
- `/game_data reload` — re-read the override tables and publish a new snapshot;
- `/game_data mod <mod-id> <stat-index> <min> <max>` — set a range;
- `/game_data clear_mod <mod-id> [stat-index]`;
- `/game_data limit <key> <value>` / `clear_limit <key>`.

The item-template command (`/item_template <id>`) is planned with phase 5. Catalogue rows can be edited directly in
`catalog_entries` (one JSON payload per typed row); `/game_data reload` republishes them. A future panel should write
through `GameDataStore` rather than editing the JSON by hand.

A future admin panel can call the same `GameDataStore` and reload service; it must not write SQLite directly and then
expect the running Gateway to notice. The supported path is: validate, write one transaction, rebuild the affected
snapshot, publish, log the new revision. Cross-process invalidation is not needed for the Gateway today; if a second
server process edits the same file later, add a `revision` check or a file-watcher reload.

## Implementation phases

1. **Foundation (done).** `GameDataStore` schema, startup load, immutable snapshot, `/game_data reload`, tests and this
   document. The reference mod/base lists are warmed at startup. No behaviour change when the tables are empty.
2. **Mod ranges (done).** `ModRangeProvider`, effective ranges in `Mod`, every direct `.Min`/`.Max` consumer routed
   through `RangeAt`/`MaxValues`, DB set/clear commands, tests. This proves the no-restart cache.
3. **Limits (done).** `LimitSettings` for timeless, radius jewels, Impossible Escape and tattoo groups; the hard-coded
   checks now read the effective limit; tests cover the changed group limit.
4. **Content catalogues (done).** `catalog_entries` stores unique items, radius jewels, threshold jewels, unique
   jewels, timeless jewels, tattoo effects and unique jewel art. The current code arrays seed each kind on the first
   run; after that the database is the source. `GameDataCatalog` swaps the typed arrays/dictionaries on reload.
5. **Item templates + custom name (next).** Add `Item.CustomName`, save it, add a template validator and
   `/item_template`; tests for existing base + existing mods + custom name + relog. The `item_templates` schema is in
   place but has no reader/writer yet.
6. **Admin UI.** A small local panel (HTTP/HTML or an in-client dev panel) over the same service, with validation and a
   revision display. Decide the transport before building it; do not make the server parse form data in the hot path.
7. **Broader settings.** Drop chances, vendor prices, crafting costs and other server-only knobs, one typed provider at
   a time.
8. **Remaining content catalogues.** NPC shops and placements, drop tables, then the gem/utility/monster mapping lists.
   Each move keeps the current numbers as the seed and adds a live comparison test against the old code path.

## Acceptance checks

- With empty override tables, a generated item and a socket check behave exactly as today.
- Set a mod range, create a new item without restarting, and see a value inside the new range; a saved old item keeps its
  old value.
- Set a limit to 2, socket a second jewel, and see it accepted; set it to 0 and see unlimited; clear it and see the base
  rule again.
- Create a custom item from an existing base and existing mods with a custom name, relog, and see the same name/mods.
- Change a range, restart the Gateway, and see the override persist.
- Change a range while another connection is rolling items; every generated value is from either the old or the new
  snapshot, never a partially updated table.
- A failed validation or SQLite write leaves the old snapshot and does not change the item.

Live check 2026-10-30 (Gateway and real client):

- `/game_data list` on the empty overlay printed revision 1 with 0 overrides.
- `/game_data mod LocalAddedPhysicalDamage9 0 100 100` published revision 2; `/game_data list` showed
  `LocalAddedPhysicalDamage9[0] = 100..100`.
- `/game_data limit timeless_jewel 2` published revision 3; `list` showed both rows.
- Clearing both rows published revision 5 with 0 overrides. The three tables existed in `data/saves.db` and the two
  override tables were empty after the check.
- On the next startup the catalogue seed filled `catalog_entries`: 2 unique items, 76 radius jewels, 43 unique jewels
  (42 global + 1 special), 6 timeless jewels, 48 tattoo effects and 190 jewel art rows. `/game_data list` reported the
  same counts.
- Changing the `Crown of Eyes` row's `ItemLevel` from 86 to 50 in `catalog_entries`, `/game_data reload`, and
  `/item Crown of Eyes` produced an ilvl 50 item. Restoring 86 and reloading published revision 3 with the original
  values.
- The Gateway restart loaded the overlay at startup; the reference mod/base lists were warmed during that open.

## Open questions

- Should the settings live in `data/saves.db` or a separate `data/game-data.db`? The first is simpler; the second keeps
  schema ownership clean.
- Do we want a full admin web panel, an in-client UI, or commands plus an external SQLite editor for now?
- Which settings are allowed to change while characters are online, and which need a character-stat rebuild? Mod ranges
  only affect newly generated items; base/unique definitions can affect existing items on relog.
- How should a custom name interact with rare name words, magic/rare naming and the client's item filters? The wire
  format supports custom names; the UI and filter behaviour need a live check.
- Should a mod override apply to existing items? No: existing items store values, not ranges. Only future rolls and
  max-roll creation use the range. This is intentional and should be documented in the command output.
